    `loadPendingWriteCount`: `const n = await window.crateKeeper.tagger.getPendingCount(); set({ pendingWriteCount: n })`. This is the D-03 source of truth (the re-edit-aware count), NOT a derivation from the in-memory pendingEdits map.

Then `set({ isApplying:true, applyError:null, applyResult:null, writeResults:new Map() })` and `try { await window.crateKeeper.tagger.applyWrites() } catch (err) { unsub(); set({ isApplying:false, applyError: err instanceof Error ? err.message : 'Erreur inconnue' }) }`. Every Map update creates a NEW Map (no in-place mutation — locked store rule).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user click → renderer store → IPC | The Appliquer button is the only path that initiates file writes (D-01 explicit trigger) |
| main → renderer (write-event) | Per-file results render into the banner; payload is app-generated, not user HTML |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-UI-XSS | Injection | per-file error / filePath rendered in the banner | mitigate | React escapes text children by default; render filePath/error as text (no dangerouslySetInnerHTML), display the basename — no untrusted-HTML sink |
| T-05-LEAK | Resource | onWriteEvent subscription | mitigate | applyWrites subscribes before invoke and unsubscribes on done/error; the preload onWriteEvent returns an unsubscribe closure used in both paths |
| T-05-DBL | Tampering | double-click Appliquer | mitigate | `isApplying` guard returns early on re-entry; the button is `disabled` while applying; main-side controller also has an isRunning single-active guard |

No high-severity unmitigated threats remain. The only file-system threats (path traversal, atomic write, ffmpeg path) are mitigated in Plans 01-02; this renderer plan adds no new file-write surface.
</threat_model>
